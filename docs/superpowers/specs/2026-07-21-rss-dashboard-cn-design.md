# RSS 信息台设计规格

- 日期：2026-07-21
- 状态：已完成对话设计，等待用户审阅书面规格
- 上游项目：`amatya-aditya/obsidian-rss-dashboard` 2.5.0
- 仓库名：`obsidian-rss-dashboard-cn`
- 中文产品名：RSS 信息台
- Manifest 名称：RSS Dashboard CN
- 插件 ID：`rss-dashboard-cn`
- 首发平台：Obsidian 桌面端，优先支持 macOS

## 1. 背景与目标

本项目基于 RSS Dashboard 的成熟阅读、YouTube、文章正文提取和 Markdown 保存能力，面向中文个人知识工作流增加四类能力：

1. 中文界面及可维护的中英文语言包。
2. X 指定账号订阅，以及围绕个人关注主题的 X 候选内容发现。
3. 每日采集结果以开放的本地文件格式保存，供 Codex、Claude Code 或未来自动化任务继续处理。
4. 可选的多模型连接和手动 AI 操作，但任何 AI 能力都不参与每日自动采集、排序或价值判断。

第一使用场景是自用：打开 Obsidian 时，每个自然日自动刷新一次。设计同时满足未来公开 GitHub 仓库、让其他用户自行下载安装的基本条件。

## 2. 核心原则

### 2.1 插件是采集器，模型是研究员

插件只对可验证的事实负责：采集、格式统一、去重、客观筛选、阅读和保存。新颖度、观点深度、来源权威性、方法论价值及是否值得阅读，不由硬编码规则替用户判断。

### 2.2 本地文件是长期接口

Dashboard 不是数据孤岛。每天采集的结构化信息、按需取得的正文和手动生成的 AI 结果都落到本地文件，使外部模型和未来自动化可以直接读取。

### 2.3 默认不产生外部费用

RSS、YouTube 和网页阅读按上游插件的方式工作。TikHub 只在刷新 X 来源时调用；AI 只在用户主动点击按钮后调用。没有隐式备用模型、后台摘要或自动翻译。

### 2.4 以公开分享为安全基线

代码、测试夹具、示例配置和日志不得包含个人路径、真实账号清单或 API Key。私密配置与仓库、Vault 和同步目录分离。

## 3. 范围

### 3.1 第一版包含

- RSS、Atom、JSON Feed、Podcast 和上游已有媒体能力。
- YouTube 频道地址、频道 ID 和 `@handle` 转官方 RSS。
- 网站中 RSS/Atom 地址的自动发现。
- 上游阅读器中的网页正文提取和 Markdown 保存。
- X 指定账号的公开帖子采集。
- X 主题的中英文查询、排除词和可配置时间窗口。
- 每日打开 Obsidian 时按来源增量刷新。
- 客观筛选：日期、主题、来源、作者、互动数据、已读、星标和已保存。
- JSONL 每日采集底稿和中立的 Markdown 每日索引。
- 多个可选 AI 连接，以及单条内容的手动摘要、翻译、观点提取和深度分析。
- 可配置的 Markdown 模板与保存目录。
- 桌面端本地密钥文件、连接测试、调用上限和脱敏日志。

### 3.2 第一版不包含

- Obsidian 关闭时的常驻后台刷新。
- 自动 Top 10、自动摘要、自动翻译或自动价值评分。
- 根据整个 Vault 自动推断用户兴趣。
- 通用网页列表爬虫；没有 RSS 的网站需要用户提供订阅地址或 RSSHub 地址。
- YouTube 字幕获取、视频下载、音频下载或广告规避。
- X 发帖、点赞、转发、关注、私信或其他写入操作。
- 插件内的跨日期批量 AI 研究；该任务交给 Codex、Claude Code 或未来自动化。
- 第一版不支持移动端运行。手机只同步和阅读已经生成的 Markdown。

## 4. 总体架构

系统按职责拆成七个边界清晰的组件：

1. **Source adapters**：RSS/Atom/JSON Feed、YouTube RSS、TikHub X 账号、TikHub X 主题。
2. **Normalizer**：把各来源转换为统一的 `CollectedItem`，保留来源特有的客观字段。
3. **Collector**：按来源刷新、限流、重试和报告结果，不负责价值判断。
4. **Local store**：负责稳定 ID、去重、JSONL、状态、正文和手动 AI 结果。
5. **Dashboard and reader**：负责浏览、筛选、阅读、星标和保存。
6. **On-demand AI service**：只处理用户主动选择的当前条目。
7. **Secret store**：保存 TikHub 和模型密钥，仓库和 Vault 只保存非敏感连接元数据。

数据流如下：

```text
RSS / YouTube / 网站订阅 / X 账号 / X 主题查询
                         ↓
                  统一 CollectedItem
                         ↓
        去重 + 每日 JSONL + 中立 Markdown 索引
                         ↓
               Dashboard 客观筛选与阅读
                  ↙                    ↘
          一键保存 Markdown        手动调用 AI
                                      ↓
                              本地 AI 结果文件
```

各组件通过明确接口通信。TikHub、AI 服务商或本地文件实现变化时，不应迫使 Dashboard 重写。

## 5. 信息源设计

### 5.1 RSS、Atom、JSON Feed 和网站

沿用上游插件的解析、媒体识别、标签和文章阅读流程：

- 用户可直接粘贴订阅地址。
- 粘贴普通网站地址时，插件尝试发现页面声明的 RSS/Atom。
- 找不到订阅源时给出明确提示，允许用户填写 RSSHub 或自定义订阅地址。
- 每日刷新保存 Feed 提供的标题、作者、发布时间、简介、正文片段、原始链接和媒体元数据。
- 不在每日刷新中批量抓取所有网页正文。
- 用户打开普通文章时，沿用 Readability 路径抓取正文；失败时退回 Feed 自带内容。
- 一键保存时，把阅读器当前可用的最佳内容转换成 Markdown。

### 5.2 YouTube

沿用上游插件的经典处理方式：

- 支持频道 ID、频道 URL、旧式用户 URL、自定义频道 URL 和 `@handle`。
- 解析为 YouTube 官方 `feeds/videos.xml`。
- 保存标题、频道、发布时间、描述、视频 ID、封面和原始视频链接。
- 在阅读器中使用 `youtube-nocookie.com` 嵌入播放器，并保留“在 YouTube 打开”。
- 第一版不获取字幕，不下载视频、音频或图片。
- 手动 AI 操作仅能使用标题和视频描述，并在结果中明确标记“基于标题和描述”，不得伪装为基于完整视频。

### 5.3 X 指定账号

TikHub 使用只读接口 `fetch_user_post_tweet`，输入用户名或稳定用户 ID。每个账号可配置：

- 默认只显示原创帖子。
- 是否包含回复。
- 是否包含转发。
- 自定义标签和文件夹。

保存帖子全文、作者、发布时间、推文 ID、原始链接、公开互动数据、媒体链接和外部文章链接。图片和视频不下载到本地。

### 5.4 X 主题发现

主题发现不是价值推荐。它只建立一组可复现的检索条件，并保存 TikHub/X 返回的候选结果。

每个主题包含：

- 中文关键词。
- 英文关键词。
- 排除词。
- 可选重点账号。
- 时间窗口，默认 7 天，可选 1、3、7、14、30 天。

每次刷新分别保留：

- `latest`：最近新增候选。
- `top`：平台搜索返回的热门候选。

`top` 只表示平台返回顺序，不表示插件认可其新颖度、深度、权威性或价值。Dashboard 必须明确展示这个边界。

同一推文按推文 ID 去重；同一外部文章被多个账号引用时，可聚合为一条文章卡片并展示引用账号列表，但不据此自动得出“高价值”结论。

## 6. 刷新机制

### 6.1 自动刷新

- 插件在 Obsidian 布局准备完成后启动刷新检查，避免拖慢插件加载。
- 以设备本地自然日为边界，不采用严格的 24 小时间隔。
- 每个来源分别记录 `lastAttemptAt`、`lastSuccessAt`、状态和错误摘要。
- 当天成功过的来源不重复自动刷新。
- 当天失败的来源可在再次打开 Obsidian 时单独重试。
- 一个来源失败不阻塞其他来源。

### 6.2 手动刷新

提供：

- 刷新全部来源。
- 只重试失败来源。
- 刷新单个来源。

手动刷新可以绕过“今天已刷新”的限制，但仍受 TikHub 请求上限和并发限制保护。

### 6.3 未来自动化

未来如需 Obsidian 关闭时自动刷新，新增自动化任务复用相同的 `CollectedItem` 和文件目录。第一版不预埋常驻服务、端口或守护进程。

## 7. 本地存储

### 7.1 目录

沿用并扩展上游已有的 `.rss-dashboard-data`，避免引入第二套隐藏数据根目录：

```text
.rss-dashboard-data/
├── feeds/                         # 上游已有的 Feed 分片
├── collections/
│   └── 2026-07-21.jsonl           # 当天观察到的统一条目
├── content/
│   └── <item-id>.md               # 打开、保存或手动 AI 前取得的正文
├── analysis/
│   └── <item-id>/
│       └── <timestamp>-summary.md # 手动 AI 结果
└── state/                         # 刷新、去重和 schema 状态

信息收集/
├── 每日采集/
│   └── 2026-07-21.md              # 中立列表，不做价值排序
└── 已保存/                        # 一键收藏的正式知识笔记
```

所有 Vault 内路径均可配置，默认值不得包含开发者个人绝对路径。

### 7.2 `CollectedItem` 最小字段

```text
schemaVersion
id
sourceType
sourceId
sourceName
sourceBucket        # subscribed | topic-latest | topic-top
title
author
publishedAt
fetchedAt
firstSeenAt
lastSeenAt
url
guid                # Feed GUID、推文 ID 或视频 ID
observationType     # first-seen | rediscovered | metrics-updated
topics
language
excerpt
contentPath
contentBasis        # full-article | feed-content | description-only | tweet-text
metrics             # 客观互动数据
read
starred
saved
savedNotePath
collectionStatus
```

来源特有字段放在带命名空间的扩展对象中，不把 TikHub 原始响应直接暴露给 UI。

### 7.3 去重与每日快照语义

- Dashboard 和正式收藏以稳定 `id` 全局去重，同一内容不会生成多张主卡片或多篇收藏笔记。
- 每个日期文件是“当天观察快照”。滚动主题搜索再次发现旧内容时，可以在新的日期文件中再次出现，但沿用同一 `id` 并标明 `rediscovered`。
- 同一日期文件内，同一 `id` 只保留一行；后续刷新以原子重写方式合并互动数据，不追加重复行。
- `firstSeenAt` 支持判断首次发现时间，`lastSeenAt` 支持观察持续传播，Codex 可按稳定 `id` 跨日期合并。

### 7.4 文件所有权

- `collections/`、`content/` 和 `state/` 由插件管理。
- `信息收集/每日采集/` 的自动区域使用明确的开始/结束标记；插件只更新标记内区域。
- 用户或 Codex 在自动区域之外的批注不得被覆盖。
- `信息收集/已保存/` 是长期知识资产；删除订阅源不删除这些笔记。
- 同一条目重复保存时打开现有笔记，不覆盖或移入废纸篓。
- 不同条目标题相同则使用短 ID 形成不冲突的文件名。

## 8. Markdown 输出

### 8.1 每日采集索引

每日索引按客观条件组织：

- 我的订阅。
- 主题最新候选。
- 主题热门候选。
- 采集失败和内容缺失。

索引默认按发布时间倒序，不包含“最值得看”“深度最高”或 Top 10 等模型判断。

### 8.2 一键保存笔记

Frontmatter 至少包含：

```yaml
---
title:
source:
source_url:
author:
published_at:
captured_at:
source_type:
topics:
language:
content_basis:
status: 待加工
---
```

正文模板：

```markdown
## 原始内容

## AI 处理结果

## 我的加工与思考

## 相关讨论和来源
```

没有使用 AI 时，“AI 处理结果”保持为空或不生成，不插入占位式伪摘要。

## 9. 手动 AI 能力

### 9.1 服务商连接

设置页允许添加多个连接：

- Kimi。
- DeepSeek。
- 千问。
- GLM。
- OpenAI。
- Claude API。
- OpenAI 兼容中转站。
- Anthropic 兼容中转站。

每个连接包含：名称、服务商预设、协议、Base URL、模型名称、API Key 引用和是否为默认连接。具体预设 URL 和模型名属于可更新配置，不散落在业务代码中。

设置页提供连接测试。连接测试不得把 API Key 写入日志或错误报告。

### 9.2 可用操作

单条内容阅读器提供：

- 生成摘要。
- 翻译成中文。
- 提取核心观点。
- 深度分析。

以上操作全部由用户主动触发。每日刷新、打开 Dashboard、标记已读、加星和保存原文均不调用模型。

### 9.3 内容依据

调用前检查 `contentBasis`：

- 普通文章优先使用已取得的完整正文；没有正文时先尝试上游正文抓取。
- X 使用当前帖子全文及已经取得的外部文章内容。
- YouTube 第一版只使用标题和描述。
- 内容不完整时必须在确认提示和生成结果中标明依据。

### 9.4 未配置或调用失败

- 未配置连接：提示进入设置。
- API Key 失效：提示连接无效。
- 余额不足、限流、超时或中转站错误：显示可理解的失败原因。
- 不自动切换备用模型。
- 失败时不创建空白分析文件。
- 原始采集数据和已保存笔记不受影响。

### 9.5 结果保存

每次成功结果保存为独立 Markdown，记录：操作类型、生成时间、服务商、模型、内容依据和原始条目 ID。用户可选择把某次结果插入正式收藏笔记；插件不静默覆盖旧结果。

## 10. 凭证、隐私与费用

### 10.1 密钥

- 设置页可以录入密钥，但明文不写入 Vault、Git 仓库、JSONL 或普通插件日志。
- 非敏感连接元数据保存在插件配置中。
- 密钥保存在 Vault 外的桌面本地配置目录。默认路径为：macOS `~/Library/Application Support/rss-dashboard-cn/secrets.json`；Windows `%APPDATA%/rss-dashboard-cn/secrets.json`；Linux `$XDG_CONFIG_HOME/rss-dashboard-cn/secrets.json`，未设置 XDG 时回退到 `~/.config/rss-dashboard-cn/secrets.json`。
- Unix 文件权限收紧为仅当前用户可读写。Windows 使用当前用户应用数据目录，并在公开 README 中说明该文件由当前操作系统账户保护、不是端到端加密保险库。
- 第一版 Manifest 设置 `isDesktopOnly: true`，所有桌面系统共用同一 `SecretStore` 接口。
- 导出配置时只导出连接名称、协议、Base URL 和模型名，不导出密钥。

### 10.2 TikHub

- 默认使用 TikHub 官方主站 `https://api.tikhub.io`；中国大陆无代理时可手动切换直连加速地址 `https://api.tikhub.dev`，也允许配置自定义 HTTPS 源站。
- 只允许经过白名单的只读 X 接口。
- 提供每次刷新和每日最大请求数。
- UI 显示请求数量和估算费用，并明确“估算不等于账单”。
- 达到上限后停止 TikHub 请求，但 RSS、网站和 YouTube 继续工作。

### 10.3 AI 隐私

- 仅发送用户当前主动选择的内容及完成该操作所需的最少元数据。
- 不读取或上传整个 Vault。
- 每个服务商设置页显示数据将发送给第三方模型服务。
- 中转站由用户自行信任；插件不把自定义中转站描述为官方服务。

## 11. 中文界面与交互

### 11.1 国际化

- 默认语言为简体中文。
- 保留英文语言包。
- UI 字符串通过统一的 i18n key 访问，不在视图和服务中散落中英文硬编码。
- 来源返回的原始标题和正文不自动翻译。

### 11.2 Dashboard

顶部入口：

- 今日采集。
- 我的订阅。
- 主题发现。
- 已加星标。
- 已保存。
- 搜索与筛选。
- 手动刷新。

卡片展示：标题、简介、来源、作者、时间、主题、公开互动数据、内容依据及已读/星标/保存状态。

卡片或阅读器操作：打开阅读、标记已读、加星、保存 Markdown、生成摘要、翻译、提取观点、深度分析和打开原始链接。

### 11.3 添加信息源

统一入口接收 RSS、网站、YouTube 和 X 账号地址并自动识别。主题发现单独维护中英文查询、排除词和时间窗口，避免与精确订阅混淆。

### 11.4 设置分区

1. 常规。
2. 信息源。
3. 主题发现。
4. TikHub。
5. AI 模型。
6. 本地存储与 Markdown 模板。

## 12. 错误处理与可恢复性

- 来源级隔离：单源失败不影响全局。
- 状态后写：JSONL 成功落盘后才更新成功时间。
- 幂等刷新：重复运行不会制造重复条目。
- 解析失败：保存可识别的基础字段和错误状态，不能静默丢弃。
- 网页受限：退回 Feed 内容并标明 `description-only` 或 `feed-content`。
- 网络离线：保留现有 Dashboard，显示本次刷新失败，不清空数据。
- 文件冲突：不覆盖用户文件。
- 日志脱敏：认证头、密钥和带密钥 URL 不进入日志。
- 配置备份：复用并扩展上游备份服务；密钥不进入普通备份。

## 13. 自用安装与公开发布

### 13.1 本地安装

生产构建产出：

```text
main.js
manifest.json
styles.css
```

把文件放入：

```text
<vault>/.obsidian/plugins/rss-dashboard-cn/
```

在 Obsidian 第三方插件设置中启用。插件 ID 和目录名一致，因此可以与上游 `rss-dashboard` 并存测试。

Manifest 使用 Basic Latin 名称 `RSS Dashboard CN`，中文界面内显示“RSS 信息台”，为未来提交 Obsidian 社区目录保留命名兼容性。

### 13.2 GitHub 公开条件

- 保留上游 MIT `LICENSE` 和原作者版权声明。
- README 明确说明项目是社区 Fork、上游地址和主要差异。
- 不把个人主题词、账号清单、绝对路径、API Key 或真实调用日志提交到仓库。
- 提供不含密钥的示例配置。
- 提供隐私说明、TikHub 第三方服务说明和 AI 数据发送边界。
- GitHub Release 上传 `main.js`、`manifest.json` 和可选 `styles.css`。
- 在未通过 Obsidian 社区审核前，只描述为 GitHub 自行安装版本。

### 13.3 上游同步

## 15. 复杂度判断

本项目整体为中高复杂度，主要风险不在汉化，而在 TikHub 数据适配、多服务商边界、本地文件一致性和公开发布所需的安全基线。

参考工作量：

- 中文 i18n 与自用安装：低。
- 每日 JSONL、状态和去重：中。
- TikHub 账号订阅：中。
- X 主题发现及费用保护：中高。
- 多模型设置和手动 AI：中高。
- 完整测试、实机验证和公开说明：中高。

在不扩展字幕下载、通用网页爬虫、移动端和自动 AI 排序的前提下，第一版边界可控，并保留未来自动化演进空间。

## 16. 已确认的关键决策

1. 采用 Fork 上游并做本地文件优先的插件改造。
2. Mac 打开 Obsidian 时，每个自然日自动刷新一次。
3. X 分为指定账号订阅和主题候选发现。
4. 主题由用户手动维护中英文关键词，默认回看 7 天。
5. 不做自动 Top 10、自动摘要、自动翻译或价值评分。
6. 保留多模型和中转站设置，但所有 AI 操作只由用户手动触发。
7. YouTube 和网站沿用上游成熟处理方式；第一版不获取 YouTube 字幕。
8. 每日 JSONL 保存 Feed/API 已返回的内容；网页完整正文只在打开、保存或手动 AI 时获取。
9. 插件数据可被 Codex、Claude Code 和未来自动化直接读取。
10. 自用优先，同时从第一天遵守未来公开仓库需要的许可证、隐私和无密钥要求。
