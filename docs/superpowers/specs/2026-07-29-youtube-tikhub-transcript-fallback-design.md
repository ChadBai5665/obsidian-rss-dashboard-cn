# YouTube 字幕 TikHub 自动兜底设计

日期：2026-07-29
状态：用户已确认设计，待实施计划

## 1. 背景

插件当前按需获取 YouTube 字幕：先检查本地缓存，再尝试公开视频的 InnerTube 字幕轨道，失败后可调用本机 `yt-dlp`。真实 Obsidian 验收中，YouTube 对当前网络环境返回机器人验证，公开字幕和不读取浏览器 Cookie 的本机 `yt-dlp` 都可能失败，阅读器最终只能显示“公开字幕暂时不可用”。

用户已配置并验证 TikHub，希望在保留免费路径和本地缓存的前提下，把 TikHub 的 YouTube 字幕接口加入自动兜底。字幕仍然只能由明确的“获取字幕”或“重新获取”操作触发，不能随每日订阅刷新自动计费。

本设计独立于已经定位的 AI 分析 Markdown 写入问题。TikHub 字幕接入不得掩盖、绕过或顺带改写 AI 分析仓库；该 Bug 另行修复和验证。

## 2. 官方接口依据与费用边界

TikHub 官方 YouTube V2 字幕接口：

- 查询字幕或获取指定语言正文：`GET /api/v1/youtube/web_v2/get_video_captions`
- 查询异步任务结果：`GET /api/v1/youtube/web_v2/get_video_captions_result`

官方文档：

- <https://docs.tikhub.io/431829301e0>
- <https://docs.tikhub.io/492436335e0>

调用规则：

1. 不传 `language_code` 时返回可用字幕语言。
2. 传入 `language_code` 和 `format=txt` 时返回对应字幕正文。
3. 长视频可能返回 `status=processing` 和 `job_id`，随后通过结果接口轮询。
4. 字幕接口的端点价格为每次 `$0.008 USD`；正常的“列出语言 + 获取正文”首次获取预计两次，共 `$0.016 USD`。
5. 异步结果查询接口标注为免费。
6. 官方文档说明，没有字幕时可能以成功响应返回空字幕；这种查询仍可能收费。

费用提示必须使用“预计”，不能把插件记录的请求数冒充 TikHub 最终账单。插件继续使用保守的本地请求上限：只要付费端点请求已经发出，就占用一次本地额度；免费的结果轮询不占用付费额度。

## 3. 目标

- 字幕获取顺序固定为：本地缓存 → 免费 InnerTube → TikHub → 本机 `yt-dlp`。
- TikHub 只在用户明确点击字幕操作、免费方式失败且自动兜底已启用时调用。
- TikHub 成功结果进入现有本地 Markdown 字幕缓存；重新打开文章、收起面板、AI 摘要或翻译都不重复调用。
- TikHub 异步任务可跨阅读器关闭和 Obsidian 重启恢复，不能因为重新打开而创建第二个付费任务。
- 复用现有 TikHub API Key、国内/国际接口地址、连接 ID、单次上限和每日上限。
- 错误状态区分 Key、余额、额度、限流、网络、任务处理中、无字幕和响应格式变化。
- 更新插件时保护 API Key、设置、订阅、采集历史、字幕缓存、AI 结果和用户 Markdown。
- 公开发布时默认不允许 TikHub 自动获取 YouTube 字幕，防止新用户在不知情时产生费用。

## 4. 非目标

- 不在每日订阅刷新、初始历史导入或后台任务中自动获取字幕。
- 不自动下载视频或音频，不加入 Whisper/ASR。
- 不读取、复制或保存浏览器 Cookie；现有用户主动启用的 `yt-dlp --cookies-from-browser` 仍是最后一个本地回退。
- 不绕过会员、私密、年龄限制或其他需登录内容。
- 不为 TikHub 建立第二套 API Key 或第二个连接配置。
- 不自动重试已经明确失败的付费端点。
- 不在本设计中修复 AI 分析 Markdown 写入 Bug、调整模型参数或改变 AI 提示词。

## 5. 方案比较与结论

### 5.1 方案 A：免费优先，TikHub 自动兜底（采用）

优点：已有免费路径成功时零费用；YouTube 拦截当前环境时仍有稳定后备；成功后本地缓存使后续阅读和 AI 操作零新增请求。缺点：首次失败后需要一到两次付费请求，整体等待时间略长。

### 5.2 方案 B：TikHub 作为第一字幕来源

优点：路径短，成功率和响应结构更可控。缺点：每个新视频都产生费用，浪费现有免费能力，也不符合“软件只在需要时调用外部服务”的产品边界。

### 5.3 方案 C：失败后只显示独立的“使用 TikHub”按钮

优点：每次付费动作都由用户再次点击，最保守。缺点：字幕获取从一个操作变成两步，重复失败体验较重；用户已经确认希望 TikHub 自动兜底。

最终采用方案 A，同时增加独立设置开关和清晰的运行状态。对公开用户，开关默认关闭；对当前自用知识库，只有在备份现有设置后，才按本次明确授权启用。

## 6. 总体架构

### 6.1 获取链路

`YouTubeTranscriptService` 继续作为唯一业务编排入口，UI 不直接访问 TikHub：

1. 校验视频 ID 和本地条目 ID。
2. 非“重新获取”操作先读取 `{dataFolder}/content/{itemId}.md`。
3. 缓存未命中时调用 `InnerTubeTranscriptProvider`。
4. InnerTube 返回无字幕、暂时不可用或超时后，检查 TikHub 自动兜底设置、连接状态和 API Key。
5. TikHub 可用时调用 `TikHubTranscriptProvider`。
6. TikHub 未成功取得字幕时，最后检查并调用 `YtDlpTranscriptProvider`。
7. 任一提供器成功后，统一规范化字幕并通过现有内容仓库原子写入缓存。

服务层继续复用现有同条目运行协调机制。相同 `itemId + videoId + 操作类型` 的并发点击必须共享同一任务，不能创建重复网络请求。

### 6.2 TikHub 客户端边界

现有 `TikHubClient` 增加三个受控能力：

- 列出 YouTube 字幕语言。
- 获取指定语言的纯文本字幕。
- 查询指定 `job_id` 的异步结果。

前两个方法只能访问固定的付费字幕端点，并继续经过 API Key 校验、HTTPS 基地址校验、超时、响应大小、错误投影和 TikHub 额度账本。异步结果方法只能访问固定的免费结果端点；它不占用付费额度，但必须执行相同的认证、地址和响应安全检查，且不能演变成通用的“不计费请求”后门。

`TikHubTranscriptProvider` 负责把 TikHub 返回的语言和正文投影为现有字幕领域类型。轨道引用只保存语言、字幕类型和提供器内部定位信息，绝不嵌入 API Key、Authorization Header 或完整服务商响应。

### 6.3 提供器顺序

字幕服务把当前写死的两段式主提供器/回退提供器，收敛成有序提供器链。每个提供器有稳定的来源标识、可用性检查、语言列表和正文获取能力。新增来源标识 `tikhub`，缓存和界面可追溯实际字幕来源。

语言选择仍使用现有紧凑的内联选择器。TikHub 返回多种语言时，用户选择后才发送第二次付费请求；取消选择不获取正文，也不自动重发语言列表请求。

## 7. 设置与费用授权

TikHub 设置页增加：

- `允许 TikHub 自动获取 YouTube 字幕`
- 描述：只有用户点击“获取字幕”或“重新获取”、免费方式失败后才调用；首次通常为两次请求，预计 `$0.016 USD`。

持久化设置属于 TikHub 配置，默认值为关闭。开启条件：

- TikHub 总开关已开启。
- 已有稳定连接 ID。
- 外部密钥文件中存在该连接的 API Key。

缺少任一条件时不允许显示为可用，并提供“打开 TikHub 设置”入口。开关本身不测试连接、不调用字幕接口、不产生费用。

TikHub 的 X 操作和 YouTube 字幕操作共用现有单次及每日请求上限。语言列表和字幕正文各计一次；免费异步结果轮询不计入付费额度，但有独立的时间与次数上限。

## 8. 阅读器交互

### 8.1 首次获取

点击“获取字幕”后，在现有 YouTube 字幕面板中按实际阶段更新单行状态：

- 正在检查本地字幕
- 正在尝试免费字幕
- 免费字幕不可用，正在使用 TikHub
- 正在等待 TikHub 处理
- 已获取并保存到本地

成功状态显示字幕语言、人工或自动字幕、实际来源和获取时间。TikHub 被调用时补充“本次使用 TikHub N 次请求，预计费用 `$0.008` 或 `$0.016`”。没有调用时不显示费用信息。

### 8.2 缓存与重新获取

- 已有有效缓存时，“获取字幕”直接展开缓存，不访问任何提供器。
- 收起、切换文章或重新打开 Obsidian 后，继续读取同一 Markdown。
- AI 摘要、翻译、核心观点和深度分析读取缓存正文，不主动刷新字幕。
- “重新获取”才忽略当前缓存，按钮旁明确提示“免费方式失败时可能产生 TikHub 费用”。
- 重新获取仍按免费 → TikHub → `yt-dlp` 的顺序执行，不因为旧缓存来源是 TikHub 就直接付费。

不增加大型确认弹窗。用户在设置中开启自动兜底，并主动点击字幕按钮，构成一次明确授权；运行中按钮禁用并复用进行中的任务。

## 9. 异步任务与断点恢复

TikHub 返回 `processing + job_id` 时，插件必须先原子保存任务，再开始轮询。任务文件位于：

```text
{dataFolder}/state/youtube-caption-jobs.json
```

每条任务只包含：

- `itemId`
- `videoId`
- 请求语言与格式
- TikHub `jobId`
- 非秘密连接 ID
- 创建和最近查询时间
- 当前稳定状态

任务文件不得包含 API Key、Authorization Header、原始请求、字幕正文或完整 TikHub 响应。

轮询规则：

- 按官方建议间隔 2–5 秒。
- 单次前台等待最多 30 秒。
- 到时仍未完成时显示“TikHub 仍在处理”，保留“继续查询”按钮。
- 关闭面板或退出 Obsidian 不会创建新任务；再次打开文章或点击“继续查询”先读取保存的 `job_id`，只调用免费结果端点。
- 完成后先原子写入字幕缓存，再删除任务记录。
- 服务端明确表示任务无效或不可恢复时，显示“任务已失效”；不得静默创建新的付费任务。只有用户再次点击“重新获取”才能开始新任务。

应用崩溃发生在 TikHub 返回 `job_id` 与本地原子写入之间时，仍存在极小的重复创建窗口；实现应在收到响应后立即写入任务，把窗口缩到最小，并在文档中如实保留这一边界。

## 10. 本地数据与兼容性

成功字幕继续保存到：

```text
{dataFolder}/content/{itemId}.md
```

文件记录：视频 ID、字幕语言、语言名称、人工/自动、获取时间、来源和规范化正文。来源联合类型增加 `tikhub`。现有 InnerTube 和 `yt-dlp` 字幕缓存继续可读，不批量重写，也不要求重新获取。

TikHub API Key 继续以连接 UUID 保存到知识库外的桌面密钥文件。字幕缓存、任务状态、设置导出、错误信息、日志和测试夹具都不得出现密钥。

插件安装继续只替换：

- `main.js`
- `manifest.json`
- `styles.css`

不得覆盖或删除：

- 插件目录中的 `data.json`
- 桌面端外部 `secrets.json`
- `.rss-dashboard-data/`
- 订阅、采集历史、字幕缓存、AI 分析和用户 Markdown

真实知识库更新前先创建程序目录备份，并记录配置、外部密钥文件和历史目录的存在性及非秘密哈希；更新后逐项复核。不得把密钥内容打印到终端、日志、提交或验收记录。

## 11. 错误处理

TikHub 错误投影为稳定中文状态：

- 未启用 TikHub 或字幕兜底开关
- 未配置 API Key
- API Key 失效
- 余额不足
- 达到插件单次或每日额度
- TikHub 限流
- 网络失败或超时
- TikHub 正在处理
- 视频不存在、不可访问或需要登录
- TikHub 明确返回没有字幕
- TikHub 返回格式暂不支持
- 已保存的异步任务失效

规则：

- TikHub 失败后仍允许尝试本机 `yt-dlp`；若 `yt-dlp` 成功，最终结果以成功为准并记录实际来源。
- 所有来源都失败时，面板显示最有行动价值的原因，并在紧凑状态区列出各提供器的简短结果；不能只显示笼统的“字幕不可用”。
- 只有 TikHub 明确返回空字幕，或所有可用提供器都确认无轨道时，才显示“该视频没有公开字幕”。认证、网络、限流和格式错误不能被误报为“无字幕”。
- 失败不覆盖已有字幕缓存，不删除 API Key、设置、订阅、历史或 AI 结果。
- 错误文本、日志和遥测不得包含 API Key、认证头、完整 TikHub 响应或带凭证的 URL。

## 12. 测试设计

### 12.1 单元测试

至少覆盖：

1. TikHub 字幕接口只生成允许的官方路径和安全查询参数。
2. 国内、国际及合法自定义 HTTPS 基地址继续按现有规则工作。
3. 语言列表、人工/自动字幕、正文、空字幕和 `processing + job_id` 的安全解析。
4. 恶意原型、超深对象、超大响应、字段冲突和未知结构被安全拒绝。
5. 语言列表和正文分别占用一次付费额度；免费结果轮询不占付费额度。
6. Key 缺失、失效、余额不足、额度不足、限流、超时和网络错误的稳定映射。
7. 缓存命中时所有网络提供器调用次数为零。
8. InnerTube 成功时 TikHub 和 `yt-dlp` 调用次数为零。
9. InnerTube 失败后才调用 TikHub；TikHub 失败后才调用 `yt-dlp`。
10. 相同条目的重复点击共享同一运行任务。
11. 多语言选择取消时不请求正文；选择后只请求一次对应语言。
12. TikHub 成功结果以 `provider: tikhub` 写入现有 Markdown 缓存。
13. 旧版字幕缓存继续读取；失败或取消不覆盖已有缓存。
14. 异步任务先保存再轮询；重建服务后使用旧 `job_id` 免费续查，不创建第二个付费任务。
15. 完成后按“字幕缓存成功 → 删除任务”的顺序执行；任一步失败时可恢复。
16. 公开设置导出不包含 Key 或任务正文，新增开关默认关闭。
17. X 账号和主题发现继续使用同一个 TikHub 客户端与额度账本，行为不回归。

测试使用固定脱敏夹具和伪传输层，不调用真实 TikHub，也不消耗用户额度。

### 12.2 真实 Obsidian 验收

完成自动化测试、类型检查、构建、公开仓库扫描和发布包校验后：

1. 完全退出 Obsidian，备份当前插件程序目录。
2. 只替换三个发布文件，保留设置、外部密钥和 `.rss-dashboard-data`。
3. 重新打开 Obsidian，确认 TikHub 字幕兜底开关和费用说明正常。
4. 经用户再次明确授权，选择一个确定有公开字幕但免费方式失败的视频，最多发送两次 TikHub 付费字幕请求。
5. 验证字幕在阅读区显示，并写入本地 Markdown。
6. 收起、切换文章、退出并重新打开 Obsidian，确认直接恢复缓存且 TikHub 请求计数不增加。
7. 验证“重新获取”的费用提示和重复点击合并。
8. 验证 AI 内容选择器可以读取字幕缓存；AI 分析 Markdown 写入 Bug须在独立修复后单独验收。
9. 对比更新前后的 `data.json`、外部密钥状态、订阅、采集历史、字幕、AI 分析和用户 Markdown，确认无丢失或覆盖。

真实验收授权只适用于该次指定视频和最多两次字幕请求，不扩展到其他 TikHub 付费调用。

## 13. 完成标准

- 用户点击一次“获取字幕”即可完成缓存、免费获取或 TikHub 自动兜底，不需要进入设置页重复操作。
- 免费路径可用时零 TikHub 请求；TikHub 被调用时界面给出阶段和预计费用。
- 异步任务可恢复，重新打开不重复创建付费任务。
- 成功字幕成为本地 Markdown 真值，可供阅读器和 AI 操作复用。
- 所有失败均可诊断，且不破坏旧缓存和用户数据。
- TikHub X 功能、现有 YouTube 免费/本地路径、设置导入导出和发布安全检查无回归。
- 完整自动化检查、GitHub CI 和一次受控真实 Obsidian 验收全部通过后，功能才可视为完成。
