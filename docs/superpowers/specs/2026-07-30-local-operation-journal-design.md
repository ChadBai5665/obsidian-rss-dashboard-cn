# 本地运行记录中心设计

- 日期：2026-07-30
- 状态：书面规格已确认，实施计划已建立
- 适用插件：RSS Dashboard CN
- 范围：字幕、AI、订阅刷新和订阅管理的本地操作记录、查看、脱敏导出与清理

## 1. 背景

现有插件有若干分散的状态记录：

- TikHub 请求账本只保存当天已计入预算的请求总数。
- TikHub 字幕任务仓库只在服务端返回任务 ID 后保存可续查任务。
- 来源刷新账本保存最近刷新状态。
- 安全诊断只输出版本、来源和状态的汇总数量。
- 少量网络信息只写入临时开发者控制台。

这些记录不足以回答一次具体操作“什么时候开始、经过哪些阶段、停在哪里、是否可能计费、结果保存到哪里”。例如 TikHub 请求在获得任务 ID 前超时时，本地只能知道请求可能已经发送，无法还原完整过程。

本设计增加一个只保存在 Vault 内部数据目录的运行记录中心，为用户和后续维护提供可读、可关联、可脱敏的操作时间线。

## 2. 目标

1. 为每次有实际后台工作的用户操作或自动调度分配稳定的 `operationId`。
2. 将同一次操作的开始、阶段变化和最终结果聚合成一条可读时间线。
3. 覆盖字幕、AI、订阅刷新和订阅管理四类操作。
4. 明确区分手动点击、打开 Obsidian 自动刷新和定时调度。
5. 对 TikHub 明确记录已确认请求数、请求是否可能已经发送以及是否收到任务 ID。
6. 运行记录仅保存在本地；不记录凭证、正文、模型输出或原始接口响应。
7. 默认保留 30 天，总容量最多 10MB，超限时删除最旧记录。
8. 在信息台提供日常查看入口，在设置中提供脱敏导出和清空入口。
9. 日志写入失败不得中断原始业务，但必须留下“记录可能不完整”的可见状态。

## 3. 非目标

- 不记录展开、收起、滚动、筛选切换等没有后台副作用的普通界面交互。
- 不做远程遥测、云端日志上传或错误自动上报。
- 不记录 API Key、Token、Cookie、Authorization 请求头或秘密存储路径。
- 不记录字幕正文、文章正文、AI 输入、AI 输出或接口原始响应。
- 不把运行记录当作 TikHub 官方账单；实际费用仍以 TikHub 账单为准。
- 不承诺在请求超时且没有服务端任务 ID 时推断 TikHub 的最终执行结果。
- 不改变现有字幕、AI、刷新或订阅业务的成功判定。

## 4. 方案选择

采用按天保存的 JSONL 事件日志。

```text
.rss-dashboard-data/
└── state/
    └── operation-journal/
        ├── 2026-07-29.jsonl
        └── 2026-07-30.jsonl
```

每行是一条经过严格投影的事件。读取时按 `operationId` 聚合成操作摘要与时间线。

没有采用的方案：

- 每次操作单独保存 JSON：会产生大量小文件，增加 Obsidian 同步和备份负担。
- 只写开发者控制台：关闭应用后容易丢失，用户无法在插件中直接查看。

## 5. 数据模型

### 5.1 事件公共字段

每条事件只允许以下公共字段：

- `schemaVersion`：固定为 `1`。
- `eventId`：本地生成的 UUID。
- `operationId`：同一次操作共享的 UUID。
- `occurredAt`：UTC ISO 时间。
- `category`：`transcript`、`ai`、`refresh` 或 `subscription`。
- `action`：该类别内的受限动作名。
- `trigger`：`manual`、`startup`、`schedule` 或 `system`。
- `stage`：受限阶段代码。
- `status`：`started`、`progress`、`succeeded`、`failed`、`aborted` 或 `interrupted`。
- `subject`：受限的操作对象投影。
- `details`：按类别和阶段限定的非秘密字段。

事件对象拒绝额外字段、访问器属性、非普通对象、超长字符串和非有限整数。

### 5.2 操作对象

`subject` 可以包含：

- `itemId`：稳定的本地文章 ID。
- `sourceId`：稳定的本地来源 ID。
- `label`：最多 200 个字符的本地显示标题或来源名称。

运行记录界面优先使用当前数据补全显示名称；本地日志中的 `label` 使来源或文章后来被删除时仍能识别历史操作。

脱敏导出时不导出 `label`，只保留类别、状态和不可逆的短哈希关联值。

### 5.3 类别详情

#### 字幕

允许记录：

- 字幕渠道：`cache`、`innertube`、`yt-dlp`、`tikhub`。
- 阶段：检查缓存、尝试渠道、付费请求边界、收到任务、轮询、保存、完成。
- 标准错误代码。
- `confirmedPaidRequests`：`0`、`1` 或 `2`。
- `possiblySent`：布尔值。
- `jobId`：仅在 TikHub 明确返回任务 ID 后保存。
- 轮询序号和累计耗时。
- 最终内容依据：`youtube-transcript`。

#### AI

允许记录：

- AI 操作类型。
- 本地连接名称和服务商类型。
- 模型 ID。
- 阶段：准备、生成、流式接收、保存、完成。
- 标准错误代码、累计耗时和输入依据。
- 成功后的分析文档相对路径。

不得记录提示词、输入正文、流式文本或最终模型输出。

#### 刷新

允许记录：

- 刷新范围：全部、失败来源、单一来源、文件夹。
- 触发方式。
- 来源总数、成功数、失败数、新增条目数和耗时。
- 单一来源的标准化结果代码。

不得记录响应正文或包含凭证的来源地址。

#### 订阅管理

允许记录：

- 动作：新增、修改、暂停、恢复、删除。
- 来源类型、稳定来源 ID、显示名称和结果。
- 删除时是否保留采集历史。

不得记录输入中的完整 URL；界面需要显示来源时使用本地来源名称和来源 ID。

## 6. 写入和恢复

### 6.1 写入边界

`OperationJournal` 是唯一允许写运行记录的组件。业务模块只调用受类型约束的事件 API，不直接拼接 JSON。

写入流程：

1. 严格验证并复制事件。
2. 确保数据目录、状态目录和运行记录目录存在。
3. 同一 Vault 和日期的写入进入进程内队列。
4. 新日期文件使用 Obsidian 的独占创建能力创建。
5. 已存在文件使用 `DataAdapter.append` 追加完整 JSON 行和换行符。
6. 写入完成后按需执行保留策略。

### 6.2 损坏恢复

- 读取时逐行解析。
- 文件末尾没有换行或最后一行无法解析时，忽略该末行并将当天记录标记为“不完整”。
- 中间行损坏时，保留其余合法记录，并显示该日期存在损坏记录。
- 不把未知字段或非法值归一化成看似可信的事件。
- 日志损坏不得阻塞字幕、AI、刷新和订阅操作。

### 6.3 中断识别

启动插件或打开运行记录时，将超过合理时间仍只有 `started/progress`、没有终态的操作聚合显示为“可能中断”。这是读取时的展示状态，不改写历史事件。

中断判断按类别使用固定、保守的时间窗；不得把仍可能正常运行的任务提前标为失败。

## 7. 保留和容量

- 默认保留最近 30 个自然日。
- 全部运行记录总容量最多 10MB。
- 每次插件启动、每天第一次写入和手动清理后执行保留检查。
- 先删除超过 30 天的文件，再按日期从旧到新删除，直到总容量不超过 10MB。
- 不删除当天正在写入的文件，除非用户明确选择“清空全部运行记录”。
- 保留清理只操作严格受控的 `operation-journal` 目录，不递归删除未知路径。

## 8. 信息台界面

### 8.1 入口

信息台顶部新增“运行记录”按钮，与“添加订阅源”和“管理订阅源”同级。入口不是设置页面深层按钮。

点击后在信息台主区域打开运行记录视图，不叠加多层 Modal。

### 8.2 默认视图

- 默认显示最近 7 天。
- 一次操作显示为一张聚合卡片。
- 卡片标题显示操作对象和操作类型。
- 摘要显示时间、触发方式、结果、耗时和费用状态。
- 展开后按时间显示阶段时间线。
- 正在运行的操作在事件到达时更新。

### 8.3 筛选

提供：

- 类别：全部、字幕、AI、刷新、订阅。
- 状态：全部、进行中、成功、失败、可能中断。
- 日期：最近 7 天、最近 30 天。

第一版不增加全文搜索、复杂统计图和远程查询。

### 8.4 操作

- “导出脱敏记录”：生成预览，用户确认后复制。
- “清空记录”：明确说明只删除运行记录，不删除配置、密钥、订阅、字幕、采集历史、AI 分析或 Markdown；确认后执行。
- 损坏或写入失败时显示非技术化提示，并允许导出仍然可用的安全记录。

## 9. 设置入口

设置 → 导入与导出 → 诊断信息增加：

- 查看运行记录。
- 导出脱敏运行记录。
- 清空运行记录。
- 当前占用、最早记录日期和记录天数。

现有安全诊断保持兼容；新增导出内容采用单独的严格投影，不直接复制本地 JSONL。

## 10. 操作接入点

### 10.1 字幕

在 `YouTubeTranscriptService` 和 TikHub provider 的稳定业务边界记录，而不是只在按钮组件里记录：

1. 用户请求开始。
2. 缓存命中或未命中。
3. 每个字幕渠道开始和结果。
4. TikHub 请求预算确认。
5. TikHub 请求进入可能发送边界。
6. 收到同步结果或异步任务 ID。
7. 每次免费轮询及状态。
8. 超时、等待继续、失败或成功。
9. 字幕保存完成。

这样相同服务从阅读器、信息台或未来入口调用时都使用同一记录。

### 10.2 AI

由 `AiOperationTaskCoordinator` 记录：

1. 开始与输入依据。
2. 连接和模型选择。
3. 进入生成、收到第一段流式文本。
4. 进入保存。
5. 分析文档验证成功。
6. 标准失败、终止或完成。

### 10.3 刷新

由刷新编排层记录，不在每个按钮重复记录：

- 手动刷新按钮传入 `manual`。
- 打开 Obsidian 的每日刷新传入 `startup`。
- 定时器刷新传入 `schedule`。
- 记录批次统计和单来源失败摘要。

### 10.4 订阅管理

由 `SubscriptionService` 在验证后、持久化前后记录业务结果。失败事件只能保存标准错误代码，不保存用户输入的原始 URL。

## 11. 失败隔离

- 业务操作不能因为运行记录写入失败而失败。
- 每个操作上下文维护一次“记录不完整”标志，避免重复弹出通知。
- 写入失败本身只进入内存健康状态，不递归尝试写入同一个日志。
- 运行记录界面显示“最近一次日志写入失败，本次记录可能不完整”。
- 清理失败不删除当前数据，也不阻塞后续记录追加。
- 日志读取和导出设置字符数、事件数和文件大小上限，避免损坏文件造成内存失控。

## 12. 测试和验收

### 12.1 仓库

- 事件严格投影，拒绝额外字段、访问器、超长值和秘密形状。
- 新文件创建、并发追加和跨仓库实例串行化。
- 未完成末行、中间损坏、未知 schema 和超大文件的安全读取。
- 30 天清理和 10MB 上限，且不删除未知文件或其他状态文件。
- 清空只影响受控运行记录目录。

### 12.2 业务接入

- TikHub 请求在发送前失败：`possiblySent=false`。
- TikHub 请求跨过发送边界后超时：`possiblySent=true`，并保留已确认用量。
- 获得任务 ID 后的轮询、续查和最终保存形成同一 `operationId`。
- AI 流式成功后必须记录经过保存阶段和已验证文档路径。
- AI 生成成功但保存失败必须显示两个不同阶段。
- 手动、启动和定时刷新使用不同 `trigger`。
- 订阅增删改只记录来源投影，不记录原始输入 URL。

### 12.3 界面

- 同一 `operationId` 聚合为一条操作。
- 类别、状态和日期筛选正确。
- 进行中操作收到新事件后更新。
- 损坏记录显示警告但不隐藏合法操作。
- 清空前确认，取消不删除。
- 脱敏导出不含标题、URL、路径、任务 ID、API Key、正文和原始错误。

### 12.4 安装保护

更新当前 Vault 时只替换插件程序文件。安装前后验证：

- `data.json` 和外部密钥文件未改变。
- 订阅、采集历史、字幕、AI 分析和用户 Markdown 未丢失。
- 运行记录目录只在插件实际运行后创建。

## 13. 完成标准

1. 用户能从信息台打开运行记录并看到最近 7 天的聚合操作。
2. 新的字幕请求能显示从开始到终态的完整时间线。
3. 当前截图对应的 TikHub 请求超时能够明确显示“请求可能已发送、没有任务 ID、无法安全自动重发”。
4. AI、手动刷新、启动刷新和订阅管理均有可识别记录。
5. 日志不包含凭证、正文、原始响应或未脱敏错误。
6. 保留、容量、损坏恢复、导出和清空均有自动化测试。
7. 全量检查、发布包检查和当前 Vault 安装保护验证通过。
